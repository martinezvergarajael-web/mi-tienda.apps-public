Control de versiones

Qué es, qué tipos existen, cómo funcionan y cómo se usan para rastrear y gestionar cambios.

1.1 ¿Qué es el control de versiones?

El control de versiones (VCS, Version Control System) es un sistema que registra los cambios realizados sobre archivos a lo largo del tiempo, de modo que se pueda recuperar cualquier versión anterior, comparar modificaciones, saber quién cambió qué y cuándo, y trabajar en equipo sin sobrescribir el trabajo de otros.

En desarrollo móvil es indispensable: una app tiene código (Kotlin/Java/Swift/Dart), recursos, configuraciones de Gradle y dependencias que cambian constantemente y que normalmente mantienen varias personas a la vez.

1.2 Tipos de sistemas de control de versiones

Existen tres grandes modelos. Se explica cada uno con sus características, ventajas y desventajas.

A) Control de versiones local (LVCS)

Todo ocurre en el equipo del usuario. Una base de datos local guarda los cambios (deltas) de cada archivo. Ejemplo clásico: RCS; también es el “sistema” informal de copiar carpetas como proyecto_final_v2_FINAL.

Características: sin servidor, un solo usuario, historial en disco local.

  • Muy simple, no requiere red ni servidor.
  • Rápido y de bajo costo.
  • No permite colaboración.
  • Si el disco falla, se pierde todo el historial (punto único de falla).
  • Fácil equivocarse de carpeta o sobrescribir.

B) Control de versiones centralizado (CVCS)

Un servidor central guarda todas las versiones y los clientes descargan (checkout) y suben (commit) cambios a ese servidor. Ejemplos: Subversion (SVN), CVS, Perforce.

Características: repositorio único, control de permisos centralizado, historial lineal con números de revisión, los archivos se pueden “bloquear” mientras se editan.

  • Administración y permisos sencillos.
  • Todos ven el mismo estado del proyecto.
  • Buen manejo de archivos binarios grandes (Perforce).
  • Punto único de falla: si el servidor cae, nadie puede hacer commit.
  • Requiere conexión para casi todo.
  • Ramas (branches) y fusiones (merge) más pesadas y propensas a conflictos.

C) Control de versiones distribuido (DVCS)

Cada usuario clona el repositorio completo, incluido todo el historial. Se trabaja localmente y luego se sincroniza con otros repositorios (push/pull). Ejemplos: Git, Mercurial, Bazaar. Plataformas que alojan Git: GitHub, GitLab, Bitbucket.

Características: historial completo local, commits sin conexión, ramas baratas y rápidas, integridad por hash SHA.

  • Trabajo sin conexión y muy rápido.
  • Cada clon es una copia de seguridad completa.
  • Ramificación y fusión potentes; flujos de trabajo flexibles (Pull Request, Git Flow).
  • Curva de aprendizaje mayor (staging area, rebase, etc.).
  • Repositorios muy grandes o con binarios pesados ocupan mucho (se mitiga con Git LFS).
  • Sin bloqueo nativo de archivos.

1.3 ¿Cómo funciona? (ejemplo con Git)

Git maneja tres áreas: directorio de trabajo (tus archivos), área de preparación o staging (lo que irá en el próximo commit) y el repositorio (historial de commits). Cada commit es una “instantánea” del proyecto identificada por un hash único y enlazada a su commit padre.

Directorio de trabajo → git add → Staging → git commit → Repositorio local → git push → Repositorio remoto

1.4 Rastreo y gestión de cambios

El control de versiones permite rastrear cada modificación y gestionarla con estas herramientas:

Rastreo

  • git status: qué archivos cambiaron.
  • git diff: qué líneas cambiaron.
  • git log --oneline --graph: historial de commits.
  • git blame archivo: quién modificó cada línea.
  • git bisect: encuentra el commit que introdujo un error.

Gestión

  • Ramas (branch) para funciones nuevas o correcciones.
  • Merge / rebase para integrar cambios.
  • Pull Requests y revisión de código.
  • Tags para marcar versiones (v1.0.0).
  • git revert / git reset para deshacer.

Equipo

  • Resolución de conflictos de fusión.
  • .gitignore (ej. build/, local.properties).
  • Integración continua (GitHub Actions) para compilar la app.
  • Issues y tableros para organizar tareas.

1.5 Ejemplos prácticos

Ejemplo 1: Primer repositorio de una app Android

cd MiAppAndroid
git init
git add .
git commit -m "Proyecto inicial: pantalla de login"
git branch -M main
git remote add origin https://github.com/usuario/MiAppAndroid.git
git push -u origin main

Ejemplo 2: Trabajar con una rama

git switch -c feature/sensor-gps      # crear y cambiar de rama
# ... editar archivos ...
git add .
git commit -m "Agrega lectura de ubicación GPS"
git switch main
git merge feature/sensor-gps          # integrar la rama
git branch -d feature/sensor-gps      # borrar rama ya fusionada

Ejemplo 3: Deshacer y consultar

git log --oneline -5                 # últimos 5 commits
git diff HEAD~1                      # cambios vs. commit anterior
git revert a1b2c3d                   # deshace un commit creando otro
git restore archivo.kt               # descarta cambios no confirmados

Ejemplo 4: .gitignore típico de Android

*.iml
.gradle/
/local.properties
/.idea/
/build/
/captures/
.externalNativeBuild/
*.apk
*.keystore
Importante: nunca subas llaves de firma (.keystore), contraseñas ni claves de API al repositorio.
