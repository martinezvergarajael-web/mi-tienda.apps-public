Persistencia y acceso a datos

Cómo conservan y consultan información las apps móviles: archivos, bases de datos locales y remotas.

2.1 Definición

Persistencia de datos es la capacidad de una aplicación de conservar su información más allá del ciclo de vida de la ejecución: los datos siguen existiendo aunque la app se cierre, el sistema la elimine de memoria o el dispositivo se reinicie. Acceso a datos es el conjunto de mecanismos (APIs, clases, bibliotecas) con los que la app lee, escribe, actualiza y elimina esa información.

2.2 Características

Durabilidad

La información sobrevive al cierre de la app y al reinicio.

Integridad y consistencia

Los datos se mantienen válidos (transacciones, restricciones).

Seguridad

Control de acceso, aislamiento por app y cifrado.

Rendimiento

Acceso rápido; operaciones pesadas fuera del hilo principal.

Sincronización

Posibilidad de mantener coherencia entre dispositivo y nube.

Disponibilidad offline

La app funciona sin conexión usando datos locales.

2.3 Formas de persistencia en dispositivos móviles

A) Archivos

Se guardan datos en el sistema de archivos del dispositivo.

  • SharedPreferences / DataStore: pares clave-valor para configuraciones simples (tema, idioma, token). En iOS: UserDefaults.
  • Almacenamiento interno: privado de la app, se borra al desinstalar.
  • Almacenamiento externo / compartido: fotos, documentos, descargas (MediaStore, Storage Access Framework).
  • Caché: datos temporales que el sistema puede eliminar.
  • Muy simple de usar.
  • Ideal para datos pequeños o archivos binarios.
  • Sin consultas ni relaciones.
  • Difícil mantener integridad con datos complejos.

B) Bases de datos locales

Almacenan datos estructurados dentro del dispositivo. La más común es SQLite (relacional, embebida, sin servidor). Alternativas: Room (capa sobre SQLite), Realm, ObjectBox, Core Data (iOS).

  • Consultas SQL, relaciones, transacciones.
  • Funciona sin internet y es rápida.
  • Los datos quedan solo en ese dispositivo.
  • Requiere diseñar esquemas y migraciones.

C) Bases de datos remotas mediante servicios web

La app se comunica con un servidor (API REST/GraphQL) por HTTP(S) que guarda la información en una BD en la nube (MySQL, PostgreSQL, MongoDB, Firebase Firestore, Supabase). Los datos suelen viajar en formato JSON.

  • Datos compartidos entre dispositivos y usuarios.
  • Respaldo centralizado y escalable.
  • Requiere conexión y manejo de latencia/errores.
  • Necesita autenticación y seguridad del servidor.

2.5 Mecanismos de control de acceso a medios persistentes

Biblioteca de clases

Son librerías que abstraen el acceso a datos para no escribir todo a bajo nivel: Room, Jetpack DataStore, Retrofit (servicios web), Realm. Reducen código repetitivo y errores.

Clases de SQLite en Android

  • SQLiteOpenHelper: crea la BD y gestiona versiones (onCreate, onUpgrade).
  • SQLiteDatabase: ejecuta insert, query, update, delete y SQL directo.
  • ContentValues: pares columna-valor para insertar/actualizar.
  • Cursor: recorre el resultado de una consulta.
class DbHelper(ctx: Context) : SQLiteOpenHelper(ctx, "tareas.db", null, 1) {
    override fun onCreate(db: SQLiteDatabase) {
        db.execSQL("CREATE TABLE tarea(id INTEGER PRIMARY KEY AUTOINCREMENT, titulo TEXT NOT NULL, hecha INTEGER DEFAULT 0)")
    }
    override fun onUpgrade(db: SQLiteDatabase, old: Int, new: Int) {
        db.execSQL("DROP TABLE IF EXISTS tarea"); onCreate(db)
    }
}

// Insertar
val db = DbHelper(this).writableDatabase
val valores = ContentValues().apply { put("titulo", "Estudiar SQLite") }
db.insert("tarea", null, valores)

// Consultar
val c = db.query("tarea", null, null, null, null, null, "id DESC")
while (c.moveToNext()) {
    val titulo = c.getString(c.getColumnIndexOrThrow("titulo"))
}
c.close()

Mapeo relacional de objetos (ORM)

Un ORM convierte filas de tablas en objetos del lenguaje y viceversa, evitando escribir SQL manual para cada operación. En Android el estándar es Room; en iOS, Core Data / SwiftData; otras opciones: GreenDAO, Realm.

@Entity(tableName = "tarea")
data class Tarea(
    @PrimaryKey(autoGenerate = true) val id: Int = 0,
    val titulo: String,
    val hecha: Boolean = false
)

@Dao
interface TareaDao {
    @Insert suspend fun insertar(t: Tarea)
    @Query("SELECT * FROM tarea ORDER BY id DESC") fun todas(): Flow<List<Tarea>>
    @Delete suspend fun borrar(t: Tarea)
}

@Database(entities = [Tarea::class], version = 1)
abstract class AppDb : RoomDatabase() { abstract fun tareaDao(): TareaDao }

val db = Room.databaseBuilder(applicationContext, AppDb::class.java, "tareas.db").build()

2.6 Autenticación y consumo de servicios web

  1. Registro / inicio de sesión: el usuario envía credenciales por HTTPS (o usa Google, Apple, Firebase Auth).
  2. El servidor valida y devuelve un token (JWT u OAuth 2.0 access token).
  3. La app guarda el token de forma segura (EncryptedSharedPreferences / Keystore / Keychain).
  4. En cada petición, envía el token en el encabezado Authorization: Bearer <token>.
  5. El servidor responde con JSON; la app lo deserializa (Gson, Moshi, kotlinx.serialization).
  6. Si el token expira (401), se renueva con un refresh token o se pide iniciar sesión otra vez.
interface ApiService {
    @POST("login") suspend fun login(@Body cred: Credenciales): TokenResp
    @GET("tareas") suspend fun tareas(@Header("Authorization") auth: String): List<Tarea>
}

val retrofit = Retrofit.Builder()
    .baseUrl("https://api.ejemplo.com/")
    .addConverterFactory(GsonConverterFactory.create())
    .build()
val api = retrofit.create(ApiService::class.java)

// En una corrutina:
val token = api.login(Credenciales("ana@mail.com", "secreto")).token
val lista = api.tareas("Bearer $token")
Buena práctica: usa siempre HTTPS, nunca guardes contraseñas en texto plano y ejecuta las llamadas de red fuera del hilo principal.
